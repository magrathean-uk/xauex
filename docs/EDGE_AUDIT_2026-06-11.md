# XAUEX Edge Audit — 2026-06-11

Multi-agent audit (8 subsystem analysts, ~1.25M tokens, 325 tool calls) answering: how can this system make better decisions, bigger money, and be more reliable. Findings merged and ranked; the items marked **[verified]** were independently re-checked against the code after the audit. Unmarked items carry cited file:line evidence from the analysts but were not independently re-verified.

## Findings (30, ranked)

### confidence-uncalibrated-sizing — Uncalibrated LLM confidence directly scales position size
**Impact:** high | **Category:** decision | **Effort:** medium

**Evidence:** The parser system prompt (signal_parser.py:713-736) asks for '"confidence": 0.0 to 1.0' with zero definition of what the number should mean — no base rates, no anchors, no past hit-rate. That raw number then directly picks lot size: main.py:3021-3026 `if confidence >= self.config.xauex_confidence_full_threshold: return 1.0` with defaults 0.65/0.55/0.5x/0.25x (config.py:395-422), and assurance buckets at main.py:776-828 map score>=0.70 to risk_multiplier 1.5 and target_rr 2.5. Nothing in the repo measures realized hit-rate vs confidence: replay_eval.py:146-153 and shadow_trial.py:115-141 score only directional correctness of the 2h move, never bucketed by confidence, and grep shows no 'calibrat' anywhere in the codebase. The live snapshot's 0.55-confidence HOLD sits exactly on the medium-lot threshold — a coin-flip number with real sizing consequences.

**Recommendation:** Build a calibration job over the archived runs (/var/lib/xauex/signal_runs each contain signal.json with confidence) joined to shadow_trial outcomes (move_usd) and the trade journal: hit-rate per confidence decile. Remap raw LLM confidence through that table (isotonic or simple bucket map) before it reaches _xauex_lot_multiplier, and inject the current per-bucket hit-rate into the parser prompt so the model can anchor. Until measured, treat 0.55-0.68 outputs as one bucket.

### hold-rescue-fallback — Keyword-count fallback flips deliberate model HOLDs into half-size trades **[verified]**
**Impact:** high | **Category:** decision | **Effort:** small

**Evidence:** The system prompt already biases against HOLD ('Choose BUY or SELL by default... If evidence is mixed, still choose the dominant side', signal_parser.py:728-730). On top of that, _normalize_signal (signal_parser.py:503-510) overrides a model HOLD: `if allow_directional_fallback and action == 'HOLD' and not _reasoning_hard_blocker(reasoning): action = fallback['action']; confidence = max(confidence, fallback['confidence'])`. The fallback direction comes from _fallback_direction (signal_parser.py:1192-1268): regex keyword counts over news text where bullish terms include 'support', 'bid', 'long' and bearish include 'lower', 'pressure', 'capped' — words endemic to market prose — producing confidence `max(0.51, min(0.68, ...))` (line 1253), enough to clear the 0.55 medium-lot threshold. The only escape is _reasoning_hard_blocker (lines 1175-1189), a substring match for terms like 'stale'/'no data'.

**Recommendation:** Delete the HOLD-rescue path (keep fallback only for the genuinely-broken case: invalid JSON / missing action). A premium model's explicit HOLD is the most informed opinion in the pipeline — overriding it with bag-of-words counting inverts the quality ordering. If you want anti-HOLD pressure, keep it in the prompt only, where the model can weigh it against evidence.

### outcome-feedback-open-loop — Outcomes are computed but never aggregated or fed back: no hit-rate by window, regime, or confidence exists anywhere
**Impact:** high | **Category:** decision | **Effort:** medium

**Evidence:** shadow_trial.py:106-141 evaluates every archived run's 2h move ('move_usd', 'baseline_correct', 'winner') and replay_eval.py:97-153 tallies correct/incorrect per variant — but `grep shadow` over direct_predictor.py, signal_parser.py and run.py returns nothing: these outcomes are computed, emailed, and discarded. What the prompt does get is thin: _memory_summary (direct_predictor.py:417-447) is just the last 12 journal trades' raw PnL, buy/sell counts, and a loss streak label. The conditioning data exists: executor.py:551-585 deliberately promotes signal_context fields (signal_confidence, daily_trend_bias, regime_filter, etc.) to top level on closed records 'so downstream jobs (post-trade journal, weekly review) can read them directly', and signal runs carry window_label (main.py:2752) — yet the only aggregations in the codebase are weekly_review.compute_trade_metrics (weekly_review.py:69-161 — one week, direction + a single >=0.6 confidence split, consumed only by an LLM prose prompt) and the predictor's last-8 memory summary (direct_predictor.py:417). Nothing computes expectancy per window (morning/midday/us_open), per trend-alignment state, per pattern, or HOLD opportunity cost; the cost ledger (run.py:240 _append_cost_ledger_entry) is never joined against outcomes either. The April loss-recovery commit shows the owner fixes these patterns manually after drawdowns instead of the system surfacing them.

**Recommendation:** Add a deterministic (no-LLM) nightly stats job aggregating trade_journal.json + shadow outcomes + the event journal into /var/lib/xauex/performance_stats.json: expectancy and hit-rate keyed by window_label x trend_alignment x confidence bucket x pattern, plus LLM cost per window. Inject the relevant slice into the decision packet and parser/validator prompts ('do not take setups with measured hit-rate < 45% over n>=8'), the weekly review, and the dashboard. After ~60 trading days this also answers which of the three daily premium-LLM windows earns its cost — likely the fastest route to bigger net PnL and lower costs.

### snapshot-bias-misinformation — Market snapshot feeds the LLM misinformation: event flags always True, sub-noise 1d moves cast full bias votes, Polymarket sees only >50% markets at double weight
**Impact:** high | **Category:** decision | **Effort:** small

**Evidence:** (1) market_snapshot.py:92-97 maps flags to source ids (`'nfp_release_recent': {'bls_employment_situation'}` etc.) and `_event_flags` (lines 779-791) sets a flag true if ANY context item came from that source: `flag: bool(source_ids.intersection(source_set))`. But bls_employment_situation and bea_personal_income are `kind: 'html'` pages fetched every run that always return an item (context_builder.py:172-216), and RSS sources always keep their first entry even when older than the lookback (context_builder.py:146). Net effect: the dossier tells the model `cpi_release_recent: True, nfp_release_recent: True, pce_release_recent: True, fed_event_recent: True` on essentially every run (rendered at direct_predictor.py:183-188) — the live cmd.json HOLD reasoning 'mixed signals from key institutions' is exactly what a model produces when every institution appears to have 'just' released something. (2) market_snapshot.py:794-827 `_series_bias`: `if change_1d > 0: return 'SELL'` with no magnitude floor — a +0.001pp 10Y move and a +0.50pp move cast identical ±1 votes into `_overall_bias` (lines 830-859); the same class of false-precision was already fixed on the price side (direct_predictor.py:346-350 added an ATR-sized threshold). (3) polymarket.py:312-318 `_market_contribution`: `probability_edge = max(0.0, midpoint - 0.5)` — a 'Gold up today' market at 0.30 midpoint (70% implied DOWN) contributes exactly 0.0, while market_snapshot.py:849-854 gives the Polymarket bias ±2 votes versus ±1 per macro series.

**Recommendation:** Make event flags time-based (item published within 24-48h with a real timestamp, or better: derive them from the ForexFactory calendar the bot already fetches in bot/filters/news.py, which has exact event timestamps and impact ratings). Require per-series noise floors before bias votes (~2bp yields/breakevens, ~0.15 USD indexes, ~0.5 VIX, ~$0.50 WTI), otherwise NEUTRAL, and weight real-yield/USD votes above VIX/WTI. Use the signed Polymarket edge (midpoint - 0.5, negative below 0.5), net complementary up/down markets, and drop the 2x vote to parity until shadow data justifies more.

### dossier-boilerplate-freshness — Half the news dossier is JS-page boilerplate stamped 'published now, freshness 1.0'; the promised ETF-flow data is never captured
**Impact:** high | **Category:** decision | **Effort:** medium

**Evidence:** With run.py's default `--max-sources 10` (run.py:38), priority ordering in source_registry.py selects 5 static HTML pages: cftc_cot_general (40), wgc_gold_etf_flows (45), wgc_gold_trading_volumes (50), wgc_gold_reserves (55), lbma_daily_trade_reporting (60). Fetched live with the pipeline's UA, the extraction (`_fetch_page` meta-description + h1/p scrape, context_builder.py:178-200) yields 'Explore current and historical gold ETF stocks...' plus nav-bar text, '&nbsp;', '-', 'AWAITED' — zero numbers, because the data tables are JS-rendered. Each such item is stamped `published_utc=datetime.now(...)`, `freshness_hours=0.0`, `freshness_score=1.0` (context_builder.py:212-215) regardless of when the underlying release happened, and RSS entries with unparseable dates get `published = self._entry_timestamp(entry) or datetime.now(timezone.utc)` (context_builder.py:145) — maximum freshness. `_ranking_key` (context_builder.py:312-318) sorts by `-freshness_score`, so a 3-week-old BLS page outranks a genuinely fresh tier-2 RSS item. The registry claims ETF flows are 'one of the cleanest publicly available demand measures for gold' (source_registry.py:160) yet the pipeline never sees a single flow number; cftc_cot_general is fully redundant with the structured Socrata COT adapter in cftc_cot.py. Result: ~half of the 12,000-char context excerpt sent to the premium model (direct_predictor.py:32) is noise labeled fresh — the April stale-input gates hardened the structured snapshot path but this narrative path still launders stale content.

**Recommendation:** Set `auto_fetch: false` on the 5 static pages so the 10 slots fill with real RSS items (mining_gold_rss currently gets cut at priority 80). Add one structured ETF-flow adapter: SPDR GLD publishes a daily holdings CSV (spdrgoldshares.com) — total tonnes + 1d change with a real date, exactly the demand signal the registry wanted. For any remaining `_fetch_page` items, derive real freshness from the date printed on the page or the HTTP Last-Modified header, and score undated RSS conservatively (~0.3) instead of 1.0.

**Impact:** high | **Category:** decision | **Effort:** small

**Evidence:** xauex/analyst/macro_regime.py and xauex/analyst/trade_policy.py are complete LLM jobs that write /var/lib/xauex/macro_regime.json and trade_policy.json (macro_regime.py:144 'atomic_write_json(output_path, result)'; trade_policy.py:164). The bot fully consumes them: main.py:1162-1171 constructs MacroRegimeLoader/TradePolicyLoader, main.py:1949-1950 loads both before every SCALP_V1 evaluation, main.py:1995-2002 applies the macro direction gate, and trade_policy.py carries sl_buffer_multiplier/tp_rr_multiplier/aggressiveness knobs (trade_policy.py:101-114). But grep across ops/ and docs/ finds ZERO scheduler for either module — ops/install_systemd.sh installs timers only for signal windows, shadow compare/evaluate, trade journal, and weekly review (line 120). Both loaders fail open (filters/macro_regime.py:98-99 'if regime is None: return True, None'), which exactly explains the live snapshot's macro_regime={} and trade_policy={}. Same pattern: setup_scorer.py:1 claims 'polls every 5 min Mon-Fri via cron' but appears in no installer, so weekly_review.py:239 always renders 'No scored setups this week.' while its prompt still asks 'Did high-score setups outperform?' (weekly_review.py:276); morning_brief.py ('runs at 07:45 Mon-Fri via cron') is also unscheduled. The weekly review's 'Recommendations: 1-2 concrete, specific parameter or behaviour changes' (weekly_review.py:279) land in weekly_review.json/md read only by the dashboard (app/app.py:559) — nothing machine-actionable ever loops back.

**Recommendation:** Add timers: macro_regime then trade_policy sequenced ~20 minutes before each signal window, setup_scorer once at 15:05 London, plus a Monit check alerting when state.json shows macro_regime=={} during a trading session — or delete the ~600 lines of never-run code honestly. Make the weekly review also emit a machine-readable block (e.g. {"direction_cap": "SHORT_ONLY", "confidence_floor_delta": +0.05, "valid_until": ...}) that the already-built trade-policy loader reads at session start, with bounded ranges so the LLM can nudge but never rewrite risk parameters.

### shadow-trials-no-verdict — Shadow experiments never conclude and score the wrong objective (2h direction with a ±$2 HOLD band)
**Impact:** high | **Category:** decision | **Effort:** medium

**Evidence:** shadow_trial.py runs 3 compare + 3 evaluate passes per day, scoring baseline vs analyst_debate vs tradingagents_candidate into /var/lib/xauex/shadow_trials/shadow_trials.jsonl (shadow_trial.py:449-453), but the live decision mode is a static env var (signal/config.py:71-74 decision_mode default 'baseline') and the only consumer of outcomes was the retired weekly email (install_systemd.sh:95 removes xauex-shadow-report.timer); the weekly review sees only a count (weekly_review.py:245 shadow_text = f'{len(shadow)} shadow signals in history'). The score itself measures the wrong objective: shadow_trial.py:340-347 _action_is_correct — BUY 'correct' if `move_usd > 0` (even +$0.01) at exactly signal+2h (line 93), HOLD only if abs(move) <= $2 (DEFAULT_HOLD_BAND_USD, line 26) — while the live system trades SL/TP brackets with a 15:00 force-flat, so a 'correct' BUY can stop out on a $5 dip and HOLD correctness on gold ($20+/day range) is near-random; and _fetch_evaluation_price (shadow_trial.py:431-446) fetches only 240 M1 bars, silently scoring at bars[-1] — possibly days later — when the evaluate timer is delayed (lines 442-445). The bot-level shadow (EMA_PULLBACK_H1) is thinner still: a deque(maxlen=12) (main.py:1209) of unresolved 'SHADOW_READY' records (main.py:2003-2005) whose computed entry/SL/TP (scalp_v1.py:219-230) are never checked against subsequent prices — used only as a confirm-time veto (main.py:340-344). The system runs three parallel experiments and is structurally incapable of ending any of them.

**Recommendation:** Re-score trials as the bracket trades they imply: walk M1 bars first-touch from signal time to force-flat using each variant's SL/TP distances (already in the comparison record), record R-multiple expectancy, and gate any 'X beats baseline' conclusion on a Wilson confidence interval. Persist SHADOW_READY decisions to JSONL and resolve them the same way. Write a rolling verdict to /var/lib/xauex/shadow_verdict.json with an explicit promotion rule (e.g. 'debate beats baseline by >=10pp over 30 trials -> flip XAUEX_SIGNAL_DECISION_MODE'), surfaced in the weekly review and dashboard. Fail loudly when the due evaluation bar is unavailable instead of scoring the wrong timestamp.

### backtester-broken-unused — Backtester is triply broken: Rust path never triggers exits, the documented CLI crashes on launch, and TP fills are credited on the wrong side with zero costs
**Impact:** high | **Category:** decision | **Effort:** medium

**Evidence:** (1) Exits never trigger on the fast path: engine.py:384-401 checks SL/TP by iterating per-tick data (`for tick in bar.ticks: if tick.bid <= trade.stop_loss: return trade.stop_loss`), but the Rust loader builds bars WITHOUT ticks — loader.py:124-132 constructs OHLCBar with no `ticks` kwarg (dataclass default empty list, loader.py:48) and tick_parser/src/lib.rs:202-210 returns only open_time/OHLC/max_spread/tick_count. loader.py:90-92 prefers Rust whenever importable and CLAUDE.md documents `make -C xauex build && make -C xauex install` as standard setup — so with Rust installed, every trade rides to the force-close at the last bar tagged 'OPEN' (engine.py:329-334). (2) The documented CLI crashes: backtester/__main__.py:64 calls `engine = BacktestEngine(bars, env_file=args.config)` but the constructor is `__init__(self, data_dir, start_date, end_date, config=None, starting_balance=3000.0)` (engine.py:157-164) — `make backtest` (xauex/Makefile:82-89) TypeErrors immediately, and grep across README.md, AGENTS.md and docs/*.md finds zero record of why SCALP_V1 was selected as STRATEGY_MODE. (3) Fills are flattering: engine.py:393 (LONG) `if tick.ask >= trade.take_profit: return trade.take_profit` — a long closes at BID, so TP triggers a full spread early at a price the trader can't get (mirrored at :399); `_compute_pnl` (engine.py:403-412) has no commission, no swap, and a hardcoded `pnl_usd * 0.80` GBP conversion (line 411); entry pays half of `next_bar.max_spread` (engine.py:306-310) — the MAX spread of the whole next hour, which Dukascopy rollover spikes can inflate 10x. Zero tests cover the backtester (no test file imports BacktestEngine or TickLoader).

**Recommendation:** Fix __main__.py to match the real constructor and add a smoke test running `python -m backtester` on a tiny CSV fixture. Make the Rust parser emit per-bar sequenced extremes (or resolve first-touch SL/TP inside Rust), with a regression test asserting both loader paths produce identical trade outcomes. Fix the TP trigger sides (LONG: bid >= TP; SHORT: ask <= TP), carry per-tick spread for entry, and add commission/swap/gap-aware SL fills — for a scalp-style system these costs ARE the difference between positive and negative expectancy. Require an attached backtest/shadow report for any future STRATEGY_MODE change; right now the honest answer to 'why SCALP_V1?' is unrecoverable from the repo.

### no-true-atr-fixed-bands — SL/TP are fixed $10-15 constants and nothing in the system computes true ATR — the predictor's 'ATR' and the trailing stop both use close-to-close drift **[verified]**
**Impact:** high | **Category:** profit | **Effort:** medium

**Evidence:** assets.py:42-46 hard-codes XAUUSD `min_stop_loss_distance: 10.0, max_stop_loss_distance: 15.0, min_take_profit_rr: 1.5, max_take_profit_rr: 2.5` — so max TP is $37.50 on ~$4,700 gold (~0.8%), and the strict JSON schema (signal_parser.py:808-817) plus _normalize_signal (signal_parser.py:515-521) clamp anything the model says back into that band. The atr_14 in the prompt is fake: _calculate_atr (direct_predictor.py:273-281) is `mean(abs(closes[i]-closes[i-1]))` on H1 closes — close-to-close drift, not true range — and it is only used for the momentum threshold (line 350), never for SL/TP; code comments (direct_predictor.py:346-349) admit the old thresholds 'registered sub-dollar drift as trending'. The bot's trailing stop repeats the error: main.py:3091-3102 `_xauex_recent_atr_distance` computes `ranges = [abs(curr - prev) for prev, curr in zip(closes[:-1], closes[1:])]` ×1.4, and _xauex_trailing_stop_price (main.py:3170-3193) builds structure from `window = closes[-5:]` and `return round(max(structure, atr_based), 2)` — always picking the TIGHTER stop, so intrabar wicks that pierce closes (but not actual lows) stop trades out, even though full OHLC is already fetched (`_fetch_recent_h1_ohlc_bars`, main.py:2272-2287) and only closes are kept (main.py:1509). The bot already fights the band by widening stops to `max(signal_stop, atr_stop, structure_stop)` (main.py:3941-3948), and TP stays capped at 2.5R via main.py:695-703 even in the trend regimes the system explicitly detects (TREND_ALIGNED_UPPER_THIRD_KEPT_BUY).

**Recommendation:** Compute true-range ATR(14) from the H1 high/low already available and use it everywhere: SL band = [1.0, 2.0] x ATR_H1(14) with the schema bounds generated from it per-run; allow TP up to 3.5-4R when price_features.regime_filter is TREND_ALIGNED_* (the trailing stage already protects the position), keeping the 2.5R cap only for NEUTRAL/counter-trend regimes; trail Chandelier-style (highest-high-since-entry minus k*ATR, swing lows/highs for structure, take the LOOSER of structure vs ATR). Same hit rate, materially fatter right tail — the single biggest expectancy lever.

### min-lot-risk-collapse — 0.01-lot quantization collapses the multiplier stack to three sizes, the min-lot lift silently overrides every risk cut, and the low tier can never execute **[verified]**
**Impact:** high | **Category:** profit | **Effort:** small

**Evidence:** Budget: main.py:3051-3054 `_xauex_cash_risk_budget` = min(£50, 1% × balance) = £29.55 at the live £2,955.47; sizing floors to volume_step 0.01 (sizing.py:98-99 `raw_lot = cash_risk / (stop_distance * lot_size); sized = math.floor(raw_lot / volume_step) * volume_step`, contract 100 oz). Cooldown 0.5× after 2 losses (main.py:3056-3075), US_OPEN 0.85× (main.py:3085-3086), microstructure soft 0.5× (main.py:63), and add-on 0.5× all produce reduced_risk below minimum_executable_risk ($25 = 0.01×100×25, main.py:4088-4091), and main.py:4100-4103 `allow_minimum_executable_risk_lift = (assurance.risk_multiplier >= 1.0 or ...)` plus main.py:118-119 lifts them ALL back to min lot — checking only assurance.risk_multiplier, so the post-loss cooldown's promised 50% cut (comment at main.py:3057-3065) is a no-op. The low tier is dead outright: 0.25 × £29.55 = £7.39 always returns None → ASSURANCE_RISK_BELOW_MIN_LOT (main.py:4139-4148); the canary (commit a5b5d9e) re-enables it only when `validator_status == "unavailable"` (main.py:622-632) — i.e. only when validator infra is down. Otherwise: require the COMBINED multiplier product >= ~0.7 before allowing the min-lot lift so cooldown/add-on cuts actually skip rather than silently restore full size; extend the existing canary machinery (it has per-day caps and journaling) to ordinary low-bucket CONFIRMED signals at 1-2/day so the marginal tier finally collects live samples; journal a 'QUANTIZED' flag whenever floored lot differs from raw by >25%; add the ghost slot-multiplier fields to Config or delete them; and either re-clamp assurance risk to the cap or document 1.5%.

**Evidence:** xauex/xauex/bot/risk/gates.py:142-143 `if pnl <= 0: self.state.consecutive_losses_today += 1` — a £0.00 or −£0.40 close (force-flat at 15:00 of a flat position, or a protect-stop fill eroded by commission) carries identical halt weight to a full −1R loss. executor.py:538-539 feeds every non-manual close into this counter, including FORCE_FLAT_LONDON closes (main.py:4524-4525). The same counter drives the sizing cooldown (main.py:3070-3074: >=2 losses → 0.5×, >=3 → 0.3×). With .env.example's MAX_CONSECUTIVE_LOSSES=2 and WEEKLY_STOP_PCT=2.0 (£59 ≈ 2.4 full min-lot losses for a WEEK-long halt, gates.py:102-109), two near-breakeven force-flat days can halt trading while actual drawdown is under £2. Related: the weekly halt only resets if can_trade runs on a Monday — gates.py:220 `if now > start and now.weekday() == 0` — so if the service is down all Monday (plausible: reconnect_count=6 in one live session), weekly_halted persists a full extra week; the reset also never re-snapshots week_start_balance (gates.py:221-224).

**Recommendation:** Count a consecutive loss only when pnl < −max(£5, 0.25 × that trade's actual_cash_risk) (the per-trade risk is already in metadata); track scratches separately. Fix the weekly reset to compare ISO week numbers (reset whenever today's Monday > week_start's Monday) instead of requiring evaluation to land exactly on a Monday, and re-snapshot week_start_balance on reset.

### connection-failure-handling — Connection-failure handling: half-dead TCP undetected for 3 minutes, server disconnect event ignored, and an order-response timeout creates an unmanaged orphan plus double exposure
**Impact:** medium | **Category:** reliability | **Effort:** medium

**Evidence:** (1) proto_transport.py's `_heartbeat_loop` (188-196) only SENDS every 25s and `_send_heartbeat` swallows write failures entirely (`except Exception: pass`, 208-211); there is no inbound-idle deadline, so a half-dead TCP connection (NAT drop, no RST) leaves `_recv_loop` blocked in `readexactly` indefinitely while `is_connected()` stays True. The only zombie detection is the Watchdog's tick-staleness check at 180 seconds (watchdog.py:30 `_STALE_TICK_THRESHOLD = 180.0`, 63-68) — three minutes during which SL-hit/fill execution events are missed with a live position. client.py:227-228 handles the server's account-disconnect event (payloadType 2147) by only logging '[API] Account disconnected by server — will re-authenticate' — nothing re-authenticates. (2) client.py:769 waits 10s for the order response; any timeout hits `except Exception` (793-796) and returns None even though the market order may have filled; the slot is marked ORDER_NOT_PLACED (main.py:4375-4388), and when the unsolicited fill event later arrives the position is adopted with `owner=(pending_market or {}).get("owner", "strategy")` → "strategy" (main.py:4774-4794). `_monitor_xauex_positions` then skips it (main.py:4442-4443 `if tracked is None or tracked.owner != "xauex": continue` — no cash SL/TP, no force-flat) and `count_tradeable_open_positions` counts ONLY owner=="xauex" (main.py:961-963), so the next slot can open a SECOND full-risk position on top of the orphan, invisible to `_xauex_open_reserved_risk` (2848-2875). (3) The Watchdog also reconnect-storms during no-tick periods with an open position (watchdog.py:77-88 ignores stale ticks only when out-of-session AND flat), each cycle cancelling in-flight futures (client.py:191-200) — consistent with reconnect_count=6 in one live session; the counter resets on restart (watchdog.py:43,107) and nothing alerts on it.

**Recommendation:** Track last-inbound-frame time in CTraderTransport (the server heartbeats every ~25s) and force-close + fire the disconnect callback after ~75s of read silence; treat heartbeat write failures and payloadType 2147 as disconnects triggering immediate re-auth/re-subscribe instead of waiting on the 180s tick watchdog. On order timeout, record a 'pending unknown' marker keyed by clientMsgId/label and adopt label=XAUEX positions (req.label is set at client.py:767) as owner="xauex" on the next reconcile — at minimum count any non-manual open position so a possible orphan blocks new XAUEX entries, with a journal/Monit alert on unattributed positions. Persist a cumulative reconnect counter to state.json and alert when reconnects/hour exceeds ~3.

### trade-journal-fragile — Trade journal coverage is one unmonitored shot per day with silent skips — missed trades are permanently lost from the learning loop
**Impact:** medium | **Category:** reliability | **Effort:** small

**Evidence:** ops/xauex-trade-journal.timer fires once Mon-Fri at 15:07 London. post_trade_journal.run silently returns when state is >10 min stale (post_trade_journal.py:120-122: 'state.json stale or missing — skipping'), so if the bot crashed or disconnected before 15:07 (reconnect_count was 6 in one live session) the day's trades are not journalled. The source data is volatile: executor.py:192-197 _reset_closed_trades_if_new_day wipes closed_trades_today at UTC midnight, so a missed run is unrecoverable from state — those trades vanish from trade memory (history_cache.py loads only trade_journal.json), from qdrant documents (qdrant_memory.py builds docs from the same journal), and from the weekly review. A single per-trade LLM failure raises and aborts the whole run (post_trade_journal.py:141 call_claude has no try/except inside the loop; __main__ exits 1), and no Monit check watches the journal job — ops/monitoring covers morning summary, trade alerts, runtime, and signal stall only.

**Recommendation:** Make the journal idempotent-retried and durable: (1) add 2-3 timer firings (15:07, 16:30, 19:00) — the journalled_ids cursor already makes re-runs safe; (2) wrap the per-trade call_claude in try/except so one failure doesn't abort remaining trades; (3) source closed trades from the append-only event journal or broker deal history rather than the midnight-reset state snapshot, so a missed day is backfillable; (4) add a Monit check that alerts when trade_journal.json did not grow on a day state recorded closed trades. Every calibration and feedback-loop improvement depends on this file being complete.

### parser-single-sample — Single-model, single-sample decision path run at minimal reasoning; one JSON failure forfeits a whole trading window
**Impact:** medium | **Category:** reliability | **Effort:** medium

**Evidence:** The live decision is one completion: signal_parser.py:200-211 calls the parser once at temperature=0.1, max_tokens=350; for gpt-5.x models temperature is silently dropped entirely (llm_models.py:44-51 NO_TEMPERATURE_MODELS) and reasoning effort is forced to 'minimal' (llm_models.py:85 `options["reasoning"] = {"effort": "minimal", "exclude": True}`) — the premium model is deliberately run in its dumbest mode. The multi-agent modes exist (analyst_debate, tradingagents_candidate) but decision_mode defaults to 'baseline' (config.py:71-76) and they only run in offline replay/shadow. If both the json_schema and json_object attempts fail to parse (_request_json_completion, signal_parser.py:692-709), the run hard-fails to `_hold_signal(asset, 'LLM returned invalid JSON')` (lines 213-218) — at 3 windows/day, one transient provider glitch forfeits a third of the day's opportunity with no retry of a sibling model.

**Recommendation:** Two cheap changes: (1) add a fallback parser model (one alternate provider/model in config) tried before giving up on the window — the per-call cost at gpt-oss-120b pricing ($0.15/$0.60 per M, llm_models.py:12) is fractions of a cent; (2) for the live path, sample the parser 2-3 times (or parser + one diverse model) and require directional majority, using vote agreement as an empirical confidence input — this also gives the confidence-calibration finding a grounded signal. Reconsider 'minimal' reasoning effort for the one call per window that decides real money.


## Subsystem summaries

### Signal & prediction core

The LLM core is a single-pass pipeline: run.py builds a context bundle (RSS items, FRED/macro market snapshot, Polymarket, COT, last 8 journal trades, Qdrant snippets) and direct_predictor.py renders it into a markdown 'dossier' plus a compact decision packet. signal_parser.py then makes one call to the parser model (default openai/gpt-oss-120b, temperature 0.1, max_tokens 350, strict JSON schema) which returns action/confidence/SL/TP, followed by one validator call (default llama-3.3-70b-versatile) whose adjustment is capped at [-0.15, +0.10]. Mechanical guards then run: hard-stale macro HOLD, a price-bias-conflict guard below confidence 0.68, and cross-window directional persistence. SL is clamped to a fixed $10-15 band and TP to 1.5-2.5x SL from assets.py regardless of volatility; the bot later widens SL with live ATR/structure but the LLM never sees real true-range ATR. The 'confirm' pass (confirm.py -> main.py build_xauex_confirm_decision) is purely mechanical — signal age <=300s, spread <=$1, news gate, trend/shadow conflict — with no LLM and no check of how far price has drifted since the signal. Confidence is raw model output with no calibration target: it directly picks lot multipliers (>=0.65 full, >=0.55 half, else quarter) and assurance RR buckets. Shadow trials and replay_eval compute 2h directional correctness per variant but those outcomes are never joined against confidence and never fed back into the prompt — the learning loop is open. A keyword-count fallback (_fallback_direction) can convert a deliberate model HOLD into a 0.51-0.68 confidence trade, and downstream risk gating string-matches the validator's prose ('contradict' in text) rather than its structured decision.

### Market context & data

Market context is built in two parallel paths that converge in the LLM dossier. The narrative path (xauex/signal/context_builder.py) fetches the top-10-by-priority curated sources from source_registry.py (Fed RSS, BLS/BEA pages, CFTC/WGC/LBMA HTML pages), normalizes them into ranked items with freshness scores, and fails open per-source (logger.warning, line 116) but crashes the whole run only when zero items fetch (line 120). The structured path (market_snapshot.py) pulls 10 FRED series (USD indexes, nominal/real yields, breakevens, VIX, WTI, BTC) via full-history fredgraph.csv downloads with no retries, plus Fed policy context (FOMC calendar + 3 more FRED series), a Socrata CFTC COT adapter, an optional CME FedWatch API (unconfigured by default), and an optional Polymarket adapter (disabled by default). Failed FRED series cascade through a Fed H.15 fallback (yields/breakevens only) then an archived-snapshot fallback, each demoting freshness to 'warning'; freshness hard-blocks during live windows when 2+ series are missing, 3+ series exceed 7 days, or an FOMC blackout applies, and signal_parser.py adds a stricter 2-business-day gate on daily-publishing series plus suppression of keyword-fallback rescues whenever the state is warning or worse. The audit found that degraded data mostly does block correctly on the structured path, but the narrative path systematically launders staleness: HTML pages and undated RSS entries are stamped freshness 1.0/published-now, event flags (cpi/nfp/pce/fed 'recent') are effectively always True because they test only source presence, and roughly half the dossier slots carry JS-page marketing boilerplate (the WGC 'ETF flows' source delivers zero actual flow numbers — verified live). The biggest single stale-input risk to expectancy is that both USD indexes are weekly-lag H.10 series explicitly exempted from the stale gate, so the model makes intraday gold calls on week-old USD direction even though a live cTrader FX quote feed already exists. Reliability-wise, FRED is a single point of failure fetched in the heaviest possible way (13 full-history CSVs per run, 20s timeout, no retries), which is the plausible root cause of the repeated source-blocked HOLDs the new stall monitor was built to catch — and that monitor itself is blind to total outages (no archived runs → no alert), while the bot's news-calendar cache fallback un-halts trading with unlimited staleness despite a docstring promising fail-closed behavior.

### Risk & sizing

XAUEX sizes trades from a cash-risk budget: min(£50, 1% of balance) = £29.55 on the live £2,955 account (main.py:3051-3054), scaled by an assurance multiplier (1.5×/1.0×/0.25× for high/medium/low buckets, main.py:776-829), a post-loss cooldown (0.5× after 2 losses), a per-slot multiplier, and add-on/counter-signal/microstructure multipliers, then converted to lots via floor(cash_risk/(sl_distance×100)) with floor-to-step-never-round-up (sizing.py:84-105). The stop is the WIDEST of signal/ATR/structure, bounded into [10, max(2×signal, 25)] (main.py:666-677, 3938-3948), so sl_distance commonly hits $25 — at which point the minimum 0.01 lot already represents $25 of risk and every multiplier collapses to the same min-lot trade (high = medium = cooldown-halved = add-on), with a 'minimum executable risk lift' (main.py:94-120, 4100-4113) silently restoring any reduced risk back to min lot. Risk gates (gates.py) enforce a 2% daily drawdown stop, 5% weekly halt (Monday-only reset), 3 consecutive losses per day with pnl≤0 counting scratches as losses, plus a 3-trades/day cap, 5-minute entry windows, and a 15:00 London force-flat that clips winners while broker stops realize full −1R losses against 2.0-2.5R targets that rarely fit the remaining session. The continuation add-on correctly only adds to protected winners at 0.5× risk, but the daily-budget gate subtracts each position's ENTRY risk forever (actual_cash_risk written once at main.py:4260, read at 2848-2875), so add-ons are blocked exactly when the parent is risk-free. Three GBP-vs-USD unit mismatches run through the math: GBP budgets divided by USD stop distances (~20% under-risk), GBP broker PnL compared to USD-required protect confirmation (~27% late protection), and a USD target compared to a GBP cash-TP threshold. The low-assurance 0.25× tier can never produce an executable lot on this balance and the min-lot canary only rescues validator-outage cases, so the marginal-signal tier generates no live data at all.

### Execution & trade management

Execution is market-order-only: the XAUEX poller (main.py:3368) reads cmd.json every 10s, confirms spread/news/microstructure (main.py:265-369, spread cap $1.0), then places a plain market order with broker-side relative SL/TP (client.py:755-767) — there is no limit-order path, no slippage cap, and no spread re-check at the moment of placement. Initial stop = widest of signal/pseudo-ATR/structure stops bounded to [SL_MIN=10, max] (main.py:666-677, 3942-3948), and wide spread (>$0.80) widens the stop 1.2x rather than deferring entry (main.py:3949-3962). TP is a single full-size order at the further of model TP and a 1.5-2.5R assurance target (main.py:695-703); there are no partial take-profits. In-trade management is the OBSERVE→PROTECT→TRAIL state machine: phases advance on price progress in R (main.py:872-900, protect_r=0.85/trail_r=1.35 defaults), gated by a broker-pnl confirmation (main.py:903-942) that compares GBP pnl against USD-denominated requirements — a unit bug that silently inflates every threshold ~25%. PROTECT moves the stop to entry+0.30R; TRAIL tightens to the tighter of close-derived H1 structure and a close-to-close pseudo-ATR (main.py:3170-3193), all evaluated only in a 10-second reconcile loop (main.py:4412-4547) because XAUEX positions are excluded from the tick-driven trailing lane (executor.py:203-205). Trades close via broker SL/TP, a GBP cash backstop, or an unconditional 15:00-London force-flat that gives US_OPEN entries (13:30 London) at most ~85 minutes of life. The session R-baseline is the pre-fill quote and is never corrected to the actual fill. Highest-leverage fixes: fix the GBP/USD unit mismatch, add slippage protection and per-slot force-flat, replace the 0.85R/+0.3R choke with partial-TP-at-1R plus a real-ATR Chandelier trail, and add a fallback/alert for the cmd.json signal-key rename that may currently be silently blocking all live trades.

### Learning loop

The XAUEX learning loop is mostly write-only plumbing with two narrow feedback paths actually live. What works: the post-trade journal (systemd timer, 15:07 London) appends LLM journal entries to trade_journal.json; the signal pipeline reads the last 8 of those back into every prediction (run.py:257 → load_recent_trade_memory → memory_summary with net PnL, direction split, and consecutive-loss streak that the validator uses), and the bot's shadow EMA_PULLBACK_H1 signal acts as a confirm-time veto (main.py:340-344). Everything else is open-loop. The macro_regime and trade_policy generators — a full adaptive policy layer the bot actively loads and gates on every candle (main.py:1949-2002) — have no scheduler anywhere in ops/, so the live state's empty {} is structural: those gates have never fired. Shadow trials run 6 times a day and write outcomes to shadow_trials.jsonl, but the report email was retired and decision_mode is a static env default of 'baseline', so the baseline-vs-debate-vs-candidate experiment can never conclude or promote anything; its scoring is 2h price direction with a $2 HOLD band rather than the SL/TP economics the system actually trades. The candidate-lane metrics (completed, false_negative_wins, expectancy_usd) have no writers and sit at zero while the weekly review LLM is asked to reason over them; the setup scorer is unscheduled so the review's setup-quality section is always empty; and the review's own recommendations land in a JSON/markdown file only the dashboard displays. Qdrant memory stores trade PnL but strips it at retrieval, uses hashed bag-of-words rather than semantic embeddings, and the predictor's documented 12-trade memory window is silently capped at 8 by the loader default. Most fundamentally, no code anywhere computes regime-conditional outcome statistics — win rate by window, trend alignment, or confidence bucket — despite the executor explicitly promoting signal_context fields onto closed-trade records for exactly that purpose. When this system wins or loses, the only thing that changes is eight lines of recent-trade text in the next prompt.

### Reliability & ops

XAUEX's reliability layer is better than average for a hobby bot — atomic fsync+rename writes for state.json and cmd.json (shared/safe_io.py), HMAC-signed manual commands with TTL plus a persistent replay ledger (shared/manual_commands.py, replay_guard.py), broker-side SL/TP placed with every order, startup reconcile that restores positions and owner metadata, and a watchdog that reconnects with backoff and re-reconciles. But the protection chain has a soft core: all eight background loops (signal poller, position monitor, manual-command poller, watchdog, health server) are bare fire-and-forget asyncio tasks, and the position monitor — the only enforcer of cash stops and London force-flat — has most of its body outside any try/except, so one exception silently ends position management while main_loop keeps the process 'RUNNING'. Operational alerting cannot catch this: the Monit config carries no bot-down or health-endpoint check (the runtime check script is installed but never wired in and depends on a probe missing from the repo), the /health server on 8051 has no consumer, and the systemd OnFailure email can mathematically never fire under Restart=on-failure with 15s spacing. The service is deliberately disabled at boot and started only by a 07:25 London timer, so a mid-day host reboot leaves an open position unmanaged until next morning. Token refresh persists rotated single-use cTrader refresh tokens to a CWD-relative .env while systemd loads two EnvironmentFiles whose precedence can resurrect the stale token at restart — a silent crash-loop generator. The transport has no inbound-idle detection (heartbeats only sent, send errors swallowed, account-disconnect events ignored), leaving a 180-second blind window that matches the observed reconnect_count=6. Finally, an order-response timeout can orphan a filled position as owner='strategy', simultaneously exempting it from cash-stop management and removing the gate that blocks a second position. Stale-signal defense, by contrast, is solid: signal age capped at 300s, confirm timestamps demoted to PENDING when stale, and slot consumption persisted in risk state.

### Backtest & evaluation

Evaluation rigor is the weakest pillar of XAUEX: the live system (LLM cmd.json signals in xauex_mode, with SCALP_V1 providing M5 trend context and EMA_PULLBACK_H1 as shadow) has effectively never been validated against historical data. The backtester (xauex/backtester/) is a relic of the initial import: it simulates only the LEGACY_LEVELS H1 pattern strategy (engine.py:11-17), its documented CLI crashes with a TypeError (`BacktestEngine(bars, env_file=...)` at __main__.py:64 vs the real constructor at engine.py:157), and — fatally — its SL/TP exit check iterates `bar.ticks` (engine.py:390-400) which the recommended Rust fast path leaves empty (loader.py:124-132, lib.rs:202-210), so with tick_parser installed no trade ever closes. Even when the pure-Python path supplies ticks, TP fills are credited on the wrong side of the book (ask>=TP for longs), there is no commission/swap/slippage, and entry pays half of the next hour's MAX spread. The only live evaluation of the LLM predictor is shadow_trial.py's 2-hour direction check with a ±$2 HOLD band and raw win counts in an email — no expectancy, no SL/TP simulation, no statistical significance. The SCALP_V1-vs-EMA shadow comparison is a 12-entry in-memory deque whose decisions are never resolved to outcomes, and no document anywhere records why SCALP_V1 was chosen. There is no walk-forward or out-of-sample discipline, and no replay harness connecting the (already-archived, replayable) frozen signal runs and event journal to the bot's gate/risk logic, so every gate-tuning commit ships blind. The good news: the archive format, M1 evaluation fetcher, and event journal mean most of the missing infrastructure is assembly rather than invention.

### Strategy economics

XAUEX trades XAUUSD on a cTrader demo (£2,955 GBP) through exactly three 5-minute entry windows/day (live_windows.py:92-141: London 08:00, 11:30, NY 08:30), so the absolute ceiling is 15 windows/week; each window is single-use, an open position blocks later slots unless a protected continuation add-on fires, and xauex_max_trades_per_day=3. A directional signal must survive a 6-layer gate stack before money moves: parser hard-stale guards (signal_parser.py:64-153), a price-conflict guard that converts any sub-0.68-confidence trade contradicting price_bias into HOLD (signal_parser.py:34,336-385), directional-persistence flip blocks (directional_persistence.py:33-34,149-174), the confirm pass (spread≤$1, news, trend/shadow microstructure veto, main.py:265-369), the assurance profile (score≥0.55 for full-risk, main.py:706-829), and a min-lot floor. Sizing is cash-based: budget = min(£50, 1% of balance) = £29.55 (main.py:3051-3054), multiplied by six stacked multipliers (assurance 1.5/1.0/0.25 × cooldown × slot × counter × microstructure × continuation, main.py:94-120), then floored to 0.01-lot steps — on this balance that means 0.01-0.03 lots, and the low-assurance bucket (£7.39) is below the broker minimum for every legal stop, so it can never execute except via the 1/day canary. Stops take the WIDEST of signal ($10-15), ATR, and structure-to-daily-extreme distances (main.py:666-677), TP is stop × target_rr 1.5-2.5 (main.py:695-703,777-812), yet everything is force-flattened at 15:00 London (main.py:4524-4525) — giving the US_OPEN window ~85 minutes to travel a $24-60 TP distance while gold's H1 ATR in the live snapshot is ~$3-5, so winners actually exit via PROTECT (0.85R, lock 0.3R) and TRAIL (1.35R), pushing the break-even win rate from the designed ~34% to roughly 55-60%. The whole P&L chain confuses currencies: lot×100×sl_distance is USD but is compared against GBP budgets and GBP unrealised PnL with no FX conversion anywhere (main.py:4177,4214,4526-4529), systematically under-deploying ~20-25%. There is no written edge hypothesis anywhere (zero hits for edge/thesis/expectancy in README/docs/AGENTS); the 45/35/20 price/macro/memory weighting fed to the LLM (direct_predictor.py:10-14) is an unvalidated prior, and the live instrumentation built to measure the cost of blocked signals — candidate_metrics completed/false_negative_wins/expectancy_usd — is initialized at zero and never updated (main.py:1193-1198,2904), so the weekly review reports zeros forever. Realistically the system takes ~2-6 trades/week risking ~£20-44 each; even a strong +0.3R edge yields ~£20-40/week, while the gate thresholds (0.68, 0.65, 0.55/0.70) have never been calibrated against measured outcomes.
